## Learned User Preferences

- After a direction is agreed, continue remaining design or implementation without pausing for approval at each section.
- Prefer SEED Design System components and tokens for the typstbook preview shell; color mode is user-selectable (light, dark, or system).
- The story controls panel should be dockable to the right or bottom.

## Learned Workspace Facts

- typstbook is a Storybook-like local workbench for Typst package authors, implemented as an independent CLI plus thin web UI rather than a Storybook addon or framework.
- v1 is `typstbook init` (scaffold a package, never overwrite) and `typstbook dev`, including workbench print of the SVG preview and workbench PDF download (real `typst`-compiled PDF, not browser print-to-PDF); static docs sites, WASM render, JS CSF stories, visual regression, and Universe publishing are later.
- Stories are Typst-native `*.stories.typ` files using `#story(...)`; a later JS adapter should emit the same Story IR.
- A story is an isolated Typst compile unit covering functions, templates, set/show rules, pages, and math, with no per-kind story types.
- Extract story metadata with `typst eval` (Typst 0.15+; not deprecated `typst query`); render via the local `typst` CLI to multi-page SVG using the `{p}` output template.
- Implementation stack is TypeScript CLI + React/Vite UI (SEED Design + Tailwind) + a Typst helper package; Story IR and a `compile()` backend interface are the extension points. The JS monorepo uses pnpm workspaces (`pnpm-workspace.yaml`); do not use npm or commit `package-lock.json`.
- Optional package-root `preview.typ` exports `preview(body)` and is applied with `#show: preview` on every extract/render so shared fonts/set/show wrap story content; missing file is skipped.
- On story re-extract, merge arg defaults with live control values so new keys appear without wiping existing edits.
- Packages: `packages/typstbook` (Typst helper), `packages/server` (npm package `typstbook`; the CLI embeds the built UI), `packages/ui` (Vite UI, not published separately), `examples/demo-pkg` for dogfooding, and `examples/kice-korean` for KICE-style Korean reading exams. Do not publish as `typst` — that name is taken and would shadow the official compiler.
- `typstbook test [dir] [--update]` (packages/server/src/check.ts + snapshot.ts) compiles every story with its default args and diffs the SVG pages against `__snapshots__/<storyId>/page-NNN.svg`; exits non-zero on extract errors, compile errors, missing snapshots, or drift. `--update` (re)writes the baseline. Typst SVG output for this repo's examples is byte-identical across runs (no timestamps/randomness), so snapshot testing is stable. `examples/demo-pkg/__snapshots__` and `examples/kice-korean/__snapshots__` are committed baselines regenerated via `pnpm test:snapshots` (root script) / `.github/workflows/ci.yml` (pinned to Typst 0.15.1 via `typst-community/setup-typst@v5`).
- `StoryIR.source` (server `extractor.ts` + `source-extract.ts`, mirrored in `packages/ui/src/lib/types.ts`) is the verbatim `render:` value text (fallback: the whole `#story(...)` call) sliced directly out of the story file's raw source -- not from `typst eval`/Story IR JSON, since `render` itself is deliberately never serialized. `source-extract.ts` is a bracket/string/comment-aware scanner, not a real Typst parser, so it can miss on unusual embedded syntax (graceful degradation: `source: null`, no crash). The UI's "Show code" panel (`code-panel.tsx`) applies `substituteArgs`/`typstLiteral` (duplicated in `packages/server/src/snippet.ts` and `packages/ui/src/lib/snippet.ts` since the two packages share no lib) entirely client-side against live control values -- no server round-trip, no recompile.
- `#story()` takes an optional `description` string (plain text, not markup/content -- consistent with `title`), propagated through `emit-stories` metadata into `StoryIR.description`. The UI shows it as a one-line subtitle under the title in the canvas header.
- `typstbook build [dir] [--out dir]` (`packages/server/src/static-build.ts` + `paths.ts#resolveBuiltUiRoot`) extracts + compiles every story once with default args and writes a self-contained static copy of the built UI (`packages/ui/dist`, or the packaged `dist/ui` -- never the Vite source tree) into `--out` (default `./typstbook-static`, wiped on every run; refuses to run if `--out` equals the package root). All story data (including rendered SVG pages) is inlined as `window.__TYPSTBOOK_STATIC__` in `index.html` via a `<script>` tag (`<` escaped to `<` so embedded content can't break out of the tag) -- there is no separate JSON fetch, deliberately, so nothing needs CORS/`file://` fetch access.
- `packages/ui/vite.config.ts` sets `base: "./"` (all built asset hrefs are relative) so the same build works when served from a sub-path (e.g. a GitHub Pages project site) and not just the domain root. This does NOT make the build openable via bare `file://` -- Chromium refuses `type="module"` scripts under the `file://` (null) origin regardless of relative/absolute paths; that's a browser limitation shared by every Vite/ESM static build, not fixable from this repo. Any hardcoded absolute public-asset path in application code (not just `index.html`) must use `` `${import.meta.env.BASE_URL}foo.svg` `` instead of `"/foo.svg"` to stay base-relative -- see `story-sidebar.tsx`'s logo `<img>`.
- In static-build mode, `packages/ui/src/hooks/use-workbench.ts` reads `window.__TYPSTBOOK_STATIC__` once at module load (`STATIC_DATA`) and branches everywhere: no WebSocket connects, `selectStory` looks up precompiled pages/diagnostics from the bundled data instead of messaging the server, and `setArg` is a no-op. `useWorkbench()` returns `readOnly: Boolean(STATIC_DATA)`, threaded into `ControlsPanel`/`ArgControl` (each control `disabled={readOnly}`) and into the sidebar badge label ("static" vs "local") -- controls show default arg values but cannot be edited, since there is no compile backend to recompile against.
- `Workbench` (`packages/server/src/session.ts`) scopes `selectedId`/`argsById`/`lastGoodPages`/the compile debounce+queue per WebSocket connection (a `ClientSession`, keyed by socket, in `this.sessions`), not as single shared instance fields. `stories`/`errors` (the extracted catalog) stay shared/broadcast to every session, but `preview`/`preview-error` messages go only to the originating session's socket -- previously (single shared state) two tabs on the same `dev` server would clobber each other's selection and both receive whichever tab compiled last. `Workbench.stop()` (added for testability) closes the chokidar watcher, terminates tracked sockets, and closes `wss`/`httpServer`; `start()` returns the OS-assigned port via `httpServer.address()` (not just the requested one) so tests can pass `port: 0`. `packages/server/src/session.test.ts` spins up a real `Workbench` + two real `ws` clients to assert isolation. Because chokidar's fsevents backend can leave a few pending fs requests around briefly even after `.close()` resolves, the `test` script needs Node's `--test-force-exit` (added in v22.0.0, so within this repo's `engines.node >=22`) or `pnpm test` hangs after all tests pass.
- The UI's `?path=&args=` URL restore (`use-workbench.ts`) has a non-obvious failure mode worth knowing before touching that bootstrap logic: on the "stories" WS message's first-bootstrap branch, sending `set-args` vs. a bare `select` must NOT be decided by comparing the merged args against the client's OWN previous state (`argKeysChanged` alone) -- a brand-new server session has no args recorded for the story at all, so if the URL-restored args already equal the merge result (client-side "nothing changed"), a bare `select` seeds the fresh session from bare defaults and silently drops the restored values (control shows the right value, compiled preview doesn't). The fix compares against the story's own defaults (`current.args`) to decide whether an additional `set-args` must follow `select` on first bootstrap specifically. Caught only by an actual two-page-load browser check (open a link fresh in a new context), not by typecheck or the unit suite -- Typst's SVG export renders all text (CJK and ASCII alike) as `<use>`-referenced glyph paths, never literal `<text>` content, so verifying "did this arg change take effect" needs a value that shows up in an attribute (e.g. a fill color) or the live DOM (an input's value), not a grep over rendered SVG text.
- v1 args are JSON-serializable only (strings, numbers, booleans, hex colors, and nested arrays/dictionaries); content or markup controls are out of scope.
- Typst SVG preview pages stay light-only (white paper) regardless of workbench color mode.
- `typstbook-logo.svg` is the favicon and sidebar mark.
- PDF export (`compileStoryToPdf` in `packages/server/src/render.ts`) reuses `renderWrapperSource` from the SVG path (`compileStory`) but compiles to a single `story.pdf` (Typst infers the format from the `.pdf` extension, no `--format` flag needed) instead of per-page SVGs. It always runs in a fresh `mkdtemp` scratch dir, not a path derived from `file`+`title` like SVG's `outputDirFor` -- two PDF compiles for the same story (two tabs, or a static build overlapping a live export) previously raced on shared `rm`+`mkdir`, caught by `static-build.test.ts` flaking under concurrent `node --test` files. In `dev`, the UI POSTs a `CompileRequest` JSON body to `POST /__typstbook_pdf` (handled in `session.ts` ahead of the vite-middleware/serveStatic fallback, since that endpoint must work in both dev and built-UI mode) and gets back `application/pdf` bytes with a `Content-Disposition: attachment` header; the story title is slugged (`titleSlug`) into the filename to avoid header injection from arbitrary story titles. In `build`, `static-build.ts` compiles each story's PDF (default args only, `Promise.all`'d alongside its SVG pages) and embeds it as base64 (`StaticStory.pdf`) in the same inlined `window.__TYPSTBOOK_STATIC__` payload as the SVG pages -- no separate fetch, matching the existing static-build philosophy. `packages/ui/src/hooks/use-workbench.ts#downloadPdf` branches on `STATIC_DATA` the same way `selectStory`/`setArg` already do.
